## 一、核心方法论：实时日志驱动调试法（7步循环）

### 1.1 背景

此前调教OpenManus时采用"瞎猜"模式——任务卡住后不知道卡在哪一步、为什么卡住，只能盲目重启、反复试错。通过"实时日志驱动调试法"，在2小时内精准定位并修复10大底层bug，统帅跑批从"必卡"变为"可监控可调试"。

### 1.2 核心原则

> **不再瞎猜，一切以实时日志为准。**

- 启动任务后等待30-90秒，检查日志是否实时更新
- 日志停止更新 = 卡住了，立即诊断
- 最后一行日志 = 卡住的位置，精准定位
- 发现问题先联网搜索网友成熟方案，再动手修改

### 1.3 标准7步循环

```
第1步：启动任务
  ↓
第2步：等待30-90秒（给系统初始化时间）
  ↓
第3步：检查实时日志是否更新
  ├─ 日志正常更新 → 继续等待，进入第6步
  └─ 日志停止更新 → 进入第4步
  ↓
第4步：定位卡住点（最后一行日志 = 卡住位置）
  ↓
第5步：分析原因 + 联网搜索网友成熟方案
  ↓
第6步：修复代码（以修改代码为主，不手动干预）
  ↓
第7步：重启任务，重复循环
```

### 1.4 日志检查清单

每次检查日志时，按以下顺序查看：

| 优先级 | 日志类型 | 路径 | 检查内容 |
|--------|----------|------|----------|
| 1 | OpenManus主日志 | `logs/YYYYMMDDHHMMSS.log` | 当前执行到第几步、选择了什么工具、工具执行结果 |
| 2 | 跑批实时日志 | `logs/batch_run_ch{N}_*.log` | 跑批脚本是否在运行、当前处理到第几天、有无错误 |
| 3 | Runner输出日志 | `logs/runner_stdout*.log` | OpenManus启动状态、执行进度、最终结果 |
| 4 | 状态文件 | `logs/current_status.json` | 当前任务状态、已用时间 |
| 5 | 模型轮转记录 | `model_rotation_usage.json` | 各模型调用次数、是否正常轮转 |

## 二、异步编程4大铁律（必须遵守）

### 铁律1：异步程序中绝不能调用同步阻塞函数

**错误示例**:
```python
# ❌ 错误：同步subprocess.run会阻塞事件循环
result = subprocess.run(cmd, capture_output=True, text=True)

# ❌ 错误：同步urllib.request会阻塞事件循环
response = urllib.request.urlopen(url)
```

**正确示例**:
```python
# ✅ 正确：使用异步子进程
proc = await asyncio.create_subprocess_exec(*cmd, stdout=asyncio.subprocess.PIPE)
stdout, stderr = await proc.communicate()

# ✅ 正确：使用异步HTTP客户端（httpx/aiohttp）
async with httpx.AsyncClient() as client:
    response = await client.get(url)

# ✅ 正确：同步函数放到线程池执行
result = await asyncio.to_thread(sync_function, arg1, arg2)
```

### 铁律2：所有外部调用必须有超时设置

**必须设置超时的场景**:
- API调用（LLM、飞书、钉钉等）
- 子进程执行
- 网络请求
- 工具执行
- 数据库查询

**超时设置参考**:
| 操作类型 | 建议超时 | 说明 |
|----------|----------|------|
| LLM API调用 | 120秒 | 复杂推理可能需要较长时间 |
| 工具执行 | 60秒 | 普通工具60秒足够，长时间任务应异步化 |
| 网络请求 | 30秒 | 普通HTTP请求 |
| 子进程（短任务） | 300秒 | 5分钟 |
| 子进程（长任务/跑批） | 不等待，立即返回 | 启动后立即返回，通过日志查看进度 |

**正确示例**:
```python
# ✅ LLM调用超时
response = await asyncio.wait_for(
    self.client.chat.completions.create(**params),
    timeout=120
)

# ✅ 工具执行超时
result = await asyncio.wait_for(
    self.available_tools.execute(name=name, tool_input=args),
    timeout=60
)

# ✅ httpx客户端超时
self.client = AsyncOpenAI(
    api_key=api_key,
    base_url=base_url,
    timeout=httpx.Timeout(connect=10, read=60),
    max_retries=2
)
```

### 铁律3：日志必须实时输出

**错误示例**:
```python
# ❌ 错误：使用print，缓冲导致日志不实时
print("正在处理...")
result = subprocess.run(cmd, capture_output=True)  # 缓冲输出
```

**正确示例**:
```python
# ✅ 正确：使用logging模块，立即刷新
logger.info("正在处理...")

# ✅ 正确：子进程使用python -u禁用缓冲
proc = await asyncio.create_subprocess_exec(
    "python", "-u", script_path,
    stdout=asyncio.subprocess.PIPE
)

# ✅ 正确：逐行异步读取，实时写入日志
async def _read_stream(self, stream, log_file):
    while True:
        line = await stream.readline()
        if not line:
            break
        log_file.write(line.decode("utf-8"))
        log_file.flush()  # 立即刷新

# ✅ 正确：添加心跳机制，每30秒记录一次状态
async def _heartbeat(self, proc, log_file, stop_event):
    while not stop_event.is_set():
        try:
            await asyncio.wait_for(stop_event.wait(), timeout=30)
        except asyncio.TimeoutError:
            pass
        if proc.returncode is None:
            log_file.write(f"[HEARTBEAT] 运行中，PID={proc.pid}\n")
            log_file.flush()
```

### 铁律4：发现卡住先诊断再自愈，不要盲目重启

**卡住诊断流程**:
1. 检查最后一行日志，确定卡住位置
2. 检查进程状态（是否还在运行、CPU/内存占用）
3. 检查网络连接（API是否可达）
4. 检查资源占用（磁盘空间、内存）
5. 联网搜索类似问题的成熟方案
6. 根据诊断结果修复代码
7. 重启任务验证

**禁止行为**:
- ❌ 不看日志直接重启
- ❌ 不分析原因直接改代码
- ❌ 连续3次同样的错误还在重试
- ❌ 手动干预代替代码修复

## 三、常见问题排查清单（10大问题及解决方案）

### 问题1：OpenManus在第2步卡住，日志显示"✨ Manus's thoughts: "后无更新

**症状**:
- 第1步正常执行，选择工具并执行成功
- 第2步LLM调用成功（有Token usage记录）
- 日志显示"✨ Manus's thoughts: "（内容为空）后停止更新

**根因**:
- LLM返回的tool_calls格式可能有问题
- 或者处理tool_calls时出现异常但未记录

**解决方案**:
1. 在think方法中添加详细日志和异常处理
2. 检查response对象的类型和属性
3. 降低temperature到0.0（防止tool call malformed loops）
4. 缩小max_tokens到4096（防止输出过长导致格式错误）

**代码修复**:
```python
# 在think方法中添加详细日志
logger.info(f"📊 response type: {type(response).__name__}")
logger.info(f"📊 response dir: {[attr for attr in dir(response) if not attr.startswith('_')][:20]}")
try:
    tc_count = len(tool_calls) if tool_calls else 0
    logger.info(f"🛠️ {self.name} selected {tc_count} tools to use")
except Exception as e:
    logger.error(f"❌ Error counting tool_calls: {e}")
    tool_calls = []
```

### 问题2：batch_run工具60秒超时，但跑批脚本实际上在正常运行

**症状**:
- batch_run工具执行60秒后返回"Error: Tool 'batch_run' execution timed out after 60 seconds"
- 但实时日志显示跑批脚本正在正常运行
- OpenManus认为跑批失败，尝试重试或换策略

**根因**:
- batch_run工具的`_run_script`方法等待子进程完成（最多30分钟）
- 但toolcall.py的execute_tool方法有60秒超时
- 导致batch_run工具在60秒后被强制中断

**解决方案**:
- 修改batch_run工具，启动子进程后立即返回，不等待完成
- 后台任务持续读取子进程输出并写入实时日志
- OpenManus通过实时日志查看跑批进度
- 添加`batch_progress`工具用于查询当前进度

**代码修复**:
```python
async def _run_script(self, chapter, day, use_air):
    # 启动异步子进程
    proc = await asyncio.create_subprocess_exec(*cmd, ...)
    
    # 启动后台监控任务（不阻塞当前方法返回）
    async def _monitor():
        try:
            await asyncio.gather(
                self._read_stream(proc.stdout, log_file, ...),
                self._read_stream(proc.stderr, log_file, ...),
            )
            await proc.wait()
        finally:
            stop_event.set()
            log_file.close()
    
    monitor_task = asyncio.create_task(_monitor())
    heartbeat_task = asyncio.create_task(self._heartbeat(...))
    
    # 立即返回，不等待子进程完成
    return {
        "ok": True,
        "started": True,
        "pid": proc.pid,
        "log_file": log_path,
        "message": "跑批已启动，正在后台运行"
    }
```

### 问题5：config.toml解析失败，"Invalid statement (at line 1, column 1)"

**症状**:
- OpenManus启动失败，报错tomllib.TOMLDecodeError
- 错误位置在第1行第1列

**根因**:
- 使用PowerShell的`Set-Content -Encoding UTF8`写入文件时添加了BOM
- TOML解析器无法处理BOM

**解决方案**:
- 使用Python写入文件，确保无BOM
- 读取时使用`encoding='utf-8-sig'`自动跳过BOM

**代码修复**:
```python
# ✅ 正确：用utf-8无BOM写入
with open('config.toml', 'w', encoding='utf-8') as f:
    f.write(content)

# ✅ 正确：读取时自动跳过BOM
with open('config.toml', 'r', encoding='utf-8-sig') as f:
    content = f.read()
```

### 问题6：僵尸进程阻塞，新任务无法启动

**症状**:
- 多个OpenManus进程同时运行
- processing_users状态被阻塞
- 新任务启动后没有日志输出

**根因**:
- 之前的任务异常退出，进程没有被清理
- 多个进程同时访问同一资源导致冲突

**解决方案**:
- 启动新任务前先清理僵尸进程
- 添加进程管理机制，确保同一时间只有一个OpenManus实例运行

**清理命令**:
```powershell
Get-Process python* | Where-Object {
    $_.CommandLine -like "*openmanus*" -or $_.CommandLine -like "*main.py*OpenManus*"
} | Stop-Process -Force
```

### 问题9：python_execute工具在Windows上卡住

**症状**:
- python_execute工具执行简单代码也卡住
- 超时后返回错误

**根因**:
- 使用threading实现超时，但Windows上thread.join(timeout)不会强制终止线程
- 子线程卡住后无法被终止

**解决方案**:
- 重构为subprocess执行代码
- 创建临时文件写入代码后用subprocess执行
- 超时后子进程被强制终止

**代码修复**:
```python
async def execute(self, code, timeout=30):
    # 创建临时文件
    with tempfile.NamedTemporaryFile(mode='w', suffix='.py', delete=False) as f:
        f.write(code)
        tmp_path = f.name
    
    try:
        # 用subprocess执行
        proc = await asyncio.create_subprocess_exec(
            sys.executable, tmp_path,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE
        )
        stdout, stderr = await asyncio.wait_for(proc.communicate(), timeout=timeout)
        return {"stdout": stdout.decode(), "stderr": stderr.decode()}
    except asyncio.TimeoutError:
        proc.kill()
        return {"error": "执行超时"}
    finally:
        os.unlink(tmp_path)
```

| bridge_health | 三个标签bridge自愈 | 30秒 |
| python_execute | Python代码执行 | 30秒 |
| ask_tag_3labels | 三个标签深度思考 | 120秒 |

### 6.2 工具调用铁律

1. **长时间任务必须异步化**：启动后立即返回，通过日志查看进度
2. **所有工具必须有超时**：防止单个工具卡住导致整个任务卡死
3. **工具错误必须返回清晰信息**：不要抛出异常，返回错误字符串
4. **重复调用检测**：同工具同参数重复调用时，返回缓存结果或阻断执行
5. **失败重试上限**：同工具同参数连续失败达到上限后，阻断执行并提示换策略

## 八、自愈机制

### 8.1 三个标签bridge自愈

- 检测到标签500/连接拒绝/TargetClosed时，自动调BridgeHealth恢复
- 恢复后重试当前任务
- 最多重试2次

### 8.2 OpenManus循环检测

- base.py内置is_stuck方法，检测重复响应
- duplicate_threshold = 2，连续2次相同响应即判定为卡住
- 卡住后自动添加提示词，鼓励换策略

### 8.3 工具级自愈

- 工具执行超时后返回错误信息
- OpenManus根据错误信息决定重试或换策略
- 同工具同参数连续失败达到上限后阻断执行
