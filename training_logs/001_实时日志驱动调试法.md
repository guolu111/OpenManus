## 发现的问题

### 问题1：模型轮转不生效
- **现象**：用户发现382次调用全用2.5 Flash，3.5和Pro一次没用
- **根因**：llm.py中只有ask方法使用了current_model = self.rotator.get_next_model()，但OpenManus主要使用ask_tool方法（调用工具），该方法一直硬编码self.model（默认gemini-2.5-flash-lite）
- **影响范围**：所有需要调用工具的任务，模型轮转完全失效
- **发现方式**：用户通过API用量面板发现，然后检查llm.py代码确认

### 问题2：跑批任务卡住，日志不更新
- **现象**：跑批任务启动后，OpenManus主日志10分钟不更新，进程还在运行，看起来像卡住了
- **根因**：batch_run_tool.py的_run_script方法使用同步阻塞的subprocess.run(timeout=1800)，会阻塞OpenManus的事件循环，导致主日志无法更新。实际跑批脚本可能已退出或未启动，但subprocess.run还在等待
- **影响范围**：所有跑批任务，日志无法实时更新，无法判断任务是在运行还是已卡住
- **发现方式**：实时日志检查发现主日志停止更新，检查batch_run_tool.py代码确认

### 问题3：API调用无限等待
- **现象**：OpenManus卡在LLM调用步骤，日志停止更新，没有错误信息
- **根因**：llm.py中AsyncOpenAI客户端初始化时没有设置timeout参数，如果谷歌中转API响应慢或网络不稳定，LLM调用就会无限等待
- **影响范围**：所有LLM调用，一旦API响应慢就会卡住整个任务
- **发现方式**：检查llm.py代码发现AsyncOpenAI初始化没有timeout参数

### 问题4：asyncio未导入报错
- **现象**：OpenManus启动后报错"name 'asyncio' is not defined"
- **根因**：在ask_tool方法中使用了asyncio.wait_for()来添加超时保护，但llm.py文件开头没有导入asyncio模块
- **影响范围**：所有ask_tool调用，直接报错无法执行
- **发现方式**：OpenManus日志中显示错误信息

### 问题5：notify_feishu工具阻塞事件循环
- **现象**：OpenManus卡在第3步，准备调用notify_feishu工具，日志停止更新，将近2分钟后才开始执行工具
- **根因**：notify_feishu_tool.py的execute方法是异步的，但里面调用了同步的send_feishu(msg)函数（使用urllib.request.urlopen），同步函数在异步方法中会阻塞整个事件循环
- **影响范围**：所有调用notify_feishu工具的任务，工具调用会阻塞事件循环
- **发现方式**：实时日志检查发现"准备调用notify_feishu"和"Activating tool: notify_feishu"之间有将近2分钟延迟

### 问题6：工具执行无超时保护
- **现象**：单个工具卡住后，整个任务卡死，无法继续
- **根因**：toolcall.py的execute_tool函数没有超时设置，如果工具执行卡住（如同步阻塞、无限循环、网络等待），OpenManus就会无限等待
- **影响范围**：所有工具调用，单个工具卡住会导致整个任务卡死
- **发现方式**：检查toolcall.py代码发现execute_tool没有超时设置

### 修改2：batch_run_tool.py - 异步子进程重构
- **文件**：app/tool/batch_run_tool.py
- **修改前**：_run_script方法使用同步subprocess.run(timeout=1800)，阻塞事件循环
- **修改后**：彻底重写_run_script方法：
  - 使用asyncio.create_subprocess_exec创建异步子进程
  - 使用proc.stdout.readline()逐行异步读取，实时写入独立日志文件
  - 添加_heartbeat协程，每30秒写入一次心跳记录
  - 使用python -u参数禁用Python输出缓冲
  - 独立日志文件命名：logs/batch_run_ch{N}_{YYYYMMDD_HHMMSS}.log
- **修改原因**：同步subprocess.run阻塞事件循环，导致主日志无法更新，无法判断任务状态
- **参考来源**：联网搜索Python async subprocess实时流式输出成熟方案

### 修改3：llm.py - API超时设置
- **文件**：app/llm.py
- **修改前**：self.client = AsyncOpenAI(api_key=self.api_key, base_url=self.base_url)（无超时）
- **修改后**：
  `python
  from httpx import Timeout
  timeout = Timeout(connect=10.0, read=60.0, write=10.0, pool=10.0)
  self.client = AsyncOpenAI(
      api_key=self.api_key, 
      base_url=self.base_url,

  同时给ask_tool和ask方法添加asyncio.wait_for(timeout=120)超时保护
- **修改原因**：API调用无超时会导致无限等待，一旦网络不稳定就卡住

### 修改5：notify_feishu_tool.py - 异步化改造
- **文件**：app/tool/notify_feishu_tool.py
- **修改前**：result = send_feishu(msg)（同步调用）
- **修改后**：result = await asyncio.to_thread(send_feishu, msg)（异步包装）
- **修改原因**：同步函数在异步方法中会阻塞事件循环，导致所有日志停止更新
- **参考来源**：Python asyncio官方文档（asyncio.to_thread）

### 修改6：toolcall.py - 工具执行超时保护
- **文件**：app/agent/toolcall.py
- **修改前**：result = await self.available_tools.execute(name=name, tool_input=args)（无超时）
- **修改后**：
  `python
  try:
      result = await asyncio.wait_for(
          self.available_tools.execute(name=name, tool_input=args),
          timeout=60  # 工具执行超时60秒
      )
  except asyncio.TimeoutError:
      error_msg = f"Tool '{name}' execution timed out after 60 seconds"
      logger.error(f"⏰ {error_msg}")
      return f"Error: {error_msg}"
  `
- **修改原因**：单个工具卡住会导致整个任务卡死，必须有超时保护
- **参考来源**：Python asyncio官方文档（asyncio.wait_for）

## 经验总结

### 核心洞察
1. **异步程序中绝不能调用同步阻塞函数**——这是本次训练最重要的发现。subprocess.run、urllib.request.urlopen、requests.post等同步函数在异步方法中会阻塞整个事件循环，导致所有日志停止更新，看起来像"卡住了"，实际上是事件循环被阻塞了。
2. **所有外部调用必须有超时设置**——API调用、子进程、网络请求、工具执行，任何可能卡住的外部调用都必须有明确的超时时间，否则一旦卡住就无限等待，无法诊断也无法恢复。
3. **日志必须实时输出**——不能等全部完成后才输出，必须用readline逐行读取、实时写入日志文件，同时添加心跳机制（每30秒写一条"运行中"记录），这样才能通过日志判断任务是在正常运行还是已经卡住。
4. **实时日志驱动调试法是调教智能体的核心方法论**——不再瞎猜，一切以实时日志为准。启动任务后等待30-90秒，检查日志是否实时更新；日志停止更新=卡住了，立即诊断；最后一行日志=卡住的位置，精准定位。

### 方法论（实时日志驱动调试法7步循环）
`
1. 启动任务 → 2. 等待30-90秒 → 3. 检查日志是否实时更新
   ↓
4. 日志停止更新？→ 是 → 5. 检查最后一行日志，确定卡在哪一步
   ↓
6. 分析卡住原因（同步阻塞/无超时/API失败/参数错误）
   ↓
7. 修复问题 → 重新启动任务 → 回到第2步重复
`
直到任务顺利完成，所有步骤日志实时更新。

### 踩坑记录
1. ❌ 盲目重启：任务卡住后不看日志直接重启，导致同样的问题反复出现，浪费大量时间
2. ❌ 同步函数乱用：在异步方法中随意调用subprocess.run、urllib.request等同步函数，导致事件循环被阻塞
3. ❌ 无超时设置：API调用、工具执行都没有超时设置，一旦卡住就无限等待
4. ❌ 日志不实时：子进程输出全部完成后才返回，无法实时判断任务状态
5. ❌ 不看最后一行日志：任务卡住后不知道卡在哪一步，只能瞎猜

### 最佳实践
1. ✅ 先确保有实时日志输出，再开始调教智能体
2. ✅ 任务卡住后第一步是看日志最后一行，而不是盲目重启
3. ✅ 所有新写的异步代码，必须遵守"异步编程4大铁律"
4. ✅ 修复问题后必须重新启动验证，确认日志实时更新
5. ✅ 每次训练都要记录训练日志，形成可复现的调教档案
6. ✅ 联网搜索成熟方案，不要自己从零写代码（网友已经踩过的坑不用再踩）
