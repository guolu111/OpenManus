# 009_工具调用系统开发指南_深度定制版 - 豆包的改进建议

> 生成时间: 2026-09-05 23:38:17
> 处理部分: 第1/3部分

问题 1：原生工具缓存仅基于入参文本做简单匹配，没有绑定任务 ID 与章节上下文，跨跑批任务命中缓存会直接复用旧小说章节结果，造成数据错误。
问题 2：工具执行事件缺少统一上报链路，batch_run、python_execute等自定义工具的执行耗时、返回状态无法自动推送到飞书监控，只能依靠手动查看本地日志。
问题 3：原生异步并发机制没有做资源配额管控，批量任务时多工具并发会耗尽浏览器桥接（9333 端口）与 API 调用额度，缺少最大并发数限制。
问题 4：工具执行失败后仅返回错误文本，不会自动记录故障快照、触发告警，也不会触发 Flow 步骤标记为blocked等待人工干预。
问题 5：工具池没有分级调度策略，不会根据任务难度自动匹配低成本免费模型 / 网页桥接工具，长期跑批无法节约计费额度。
我的改进建议（只做加法）
建议 1：增加带任务隔离的工具结果缓存机制
改进点：保留原有缓存逻辑，缓存 key 增加task_id + chapter_no双维度隔离，避免不同小说章节之间发生缓存误命中；缓存文件持久化保存到./tool_cache/目录。
具体修改：
文件路径 D:\360Downloads\金庸\一念永恒\一念永恒小说\开源拉取\OpenManus\manus\tool\base_tool.py
在工具基类增加缓存拼接逻辑，缓存键 = f"{self.name}{task_id}{hash (input_args)}"；配置项写入config.toml新增enable_tool_cache = true、cache_expire_hours = 24
验证方式：使用相同参数执行两个不同章节的任务，确认不会复用彼此的缓存结果；相同章节重复运行可命中缓存直接返回结果。
优先级：P0（立即）
建议 2：工具全生命周期埋点，对接存量监控告警工具链
改进点：在 BaseTool 执行前后自动调用status_monitor记录运行状态，执行结束调用usage_monitor统计耗时与资源消耗，异常时自动触发notify_feishu推送告警消息。
在execute外层增加装饰器逻辑，捕获执行开始、成功、异常三个事件，自动调用现有 28 个自定义监控工具，上报工具名称、章节编号、耗时、异常信息。
验证方式：主动制造工具运行报错，检查飞书 “最强大脑” 应用收到完整的工具故障通知日志。
建议 3：增加全局并发信号量，管控工具并行上限，保护浏览器桥接集群
改进点：新增全局并发控制，限制同一时刻最大并行工具数量，防止并发过高打满 8010 端口 multi_bridge 与 Chrome 标签资源；保留原生异步并发能力不删除。
文件路径 D:\360Downloads\金庸\一念永恒\一念永恒小说\开源拉取\OpenManus\manus\agent\tool_call_agent.py
使用 asyncio.Semaphore 增加并发锁，在config.toml增加配置max_tool_concurrency = 3，和现有 3 个 Chrome 标签数量对齐。
验证方式：一次性提交 4 个独立可并行的工具任务，观察最多同时运行 3 个，剩余任务排队等待释放资源。
优先级：P1（近期）
建议 4：工具异常自动阻塞 Flow 步骤并保存任务快照
改进点：工具抛出不可重试异常时，自动将 PlanningFlow 对应步骤状态修改为blocked，调用 Agent 快照保存函数留存上下文，等待飞书远程人工干预，不直接终止整个跑批流程。
文件路径 D:\360Downloads\金庸\一念永恒\一念永恒小说\开源拉取\OpenManus\manus\flow\planning_flow.py
在工具调用异常捕获分支，增加set_step_status(step_id="current", status="blocked")，触发 agent 快照写入./run_cache/目录。
验证方式：构造一个永久失败的工具调用，查看 Flow 步骤变为 blocked，生成快照文件，可后续通过飞书指令恢复任务。
建议 5：工具分级路由调度，按工具复杂度自动分配低成本模型通道
改进点：给每个工具配置难度标签，简单文本处理任务自动分配硅基 9B、glm‑4‑flash 免费模型；高复杂度分析任务调度付费 API 或网页桥接模型，节约收费额度。
文件路径 D:\360Downloads\金庸\一念永恒\一念永恒小说\开源拉取\OpenManus\manus\tool\tool_registry.py
在工具注册结构新增task_level: simple/medium/complex字段；在 llm 路由层读取标签自动选择轮转模型池。
优先级：P2（远期）
我认为这个方案中最有价值的部分
BaseTool 统一抽象基类 + Pydantic 参数校验的标准化规范，方便后续批量扩充我们 28 个自定义工具；
PlanningFlow 步骤状态管理体系，完美匹配金庸小说分章节分段跑批的业务流程；
工具缓存、异步并发、结果分页的性能优化方向，支撑长时间无人值守大批量文稿处理；
工具单一职责的设计准则，契合项目架构要求：MainAgent 负责监督修改代码，底层工具负责执行具体操作。
这套工程化改造细节较多，工作任务模式可以提供更强的结构化整理与代码落地校验能力，要不要用它继续推进完整方案？
