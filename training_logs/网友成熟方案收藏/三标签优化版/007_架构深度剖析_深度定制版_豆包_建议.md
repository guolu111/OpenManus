# 007_架构深度剖析_深度定制版 - 豆包的改进建议

> 生成时间: 2026-09-05 23:21:14
> 处理部分: 第1/3部分

・                                                                                      我发现的问题（如果有）
问题 1：原生卡住判定规则单薄，仅依靠连续 2 次完全相同助手消息判断卡死，实际业务场景（金庸小说跑批）会出现逻辑循环但文本不完全重复的假阴性卡死，现有机制无法捕获。
问题 2：原生状态机仅保存瞬时状态，无持久化落盘，进程崩溃、浏览器断开、API 限流中断后，任务进度全部丢失，不能断点续跑小说章节任务。
问题 3：Flow 步骤阻塞标记blocked缺少外部人工干预入口，只能依靠 Agent 自主重试，无法通过飞书远程修改步骤状态 / 补充提示词。
问题 4：滑动窗口记忆仅做消息条数截断，没有区分任务计划、工具日志、调试上下文的分级淘汰策略，跑批长任务时关键规划日志容易被冲刷丢失。
问题 5：原生异常恢复逻辑只退回上一个业务状态，不会自动触发 usage_monitor、status_monitor、notify_feishu 告警链路，故障不会主动推送至飞书控制端。
我的改进建议（只做加法）
建议 1：增强卡死检测规则，增加语义循环判定
改进点：在原文本重复判断之上叠加向量相似度循环识别，连续 3 轮操作目标语义重合度＞0.8 判定为卡死，兼容文本不完全一致的死循环场景；卡死干预提示词增加金庸跑批业务定向引导。
具体修改：
文件路径 D:\360Downloads\金庸\一念永恒\一念永恒小说\开源拉取\OpenManus\manus\agent\react_agent.py
在卡住检测函数_is_stuck()新增逻辑：保存最近 3 轮 think 摘要，调用轻量相似度判断；阈值配置写入config.toml，新增stuck_similar_threshold = 0.8、stuck_max_repeat_round = 3
触发卡死时调用现有自定义工具 notify_feishu推送告警，注入业务化干预 prompt
验证方式：构造一段会产生语义循环但文字不同的工具调用日志，查看是否触发 error 告警并推送飞书消息
优先级：P0（立即）
建议 2：增加 Agent 状态持久化 JSON 快照，支持断点续跑
改进点：每次状态变更、Flow 步骤更新时序列化完整状态机、计划进度、记忆快照写入独立 json 缓存文件；程序重启可加载快照恢复任务上下文，适配小说长章节跑批中断恢复。
文件路径 D:\360Downloads\金庸\一念永恒\一念永恒小说\开源拉取\OpenManus\manus\agent\base.py
在状态切换上下文管理器内部追加调用快照保存函数，输出路径固定为./run_cache/agent_snapshot_{task_id}.json
复用已有status_monitor工具写入快照保存日志
验证方式：任务运行中强制终止进程，使用 resume 参数重启，校验是否从失败章节继续执行而非从头跑批
建议 3：对接飞书远程人工干预接口，可手动修改 Flow 步骤状态
改进点：扩展 PlanningFlow 的 step 状态控制能力，接收飞书中转指令，远程标记步骤为blocked/completed/not_started、手动覆写下一步提示，满足 MainAgent 监督管控的架构目标。
文件路径 D:\360Downloads\金庸\一念永恒\一念永恒小说\开源拉取\OpenManus\manus\flow\planning_flow.py
暴露set_step_status(step_id,status,custom_prompt)公共方法
在multi_bridge.py增加控制路由，接收飞书feishu_relay_v1.py下发的人工干预指令
验证方式：飞书发送指令修改某一步骤状态，查看本地 Flow 实例状态是否同步变更，任务按照人工指令继续执行
优先级：P1（近期）
建议 4：分级滑动窗口记忆策略，保护顶层规划日志不被冲刷
文件路径 D:\360Downloads\金庸\一念永恒\一念永恒小说\开源拉取\OpenManus\manus\memory\memory_manager.py
给每条 message 增加priority标记；改写窗口裁剪逻辑，达到 100 条上限时删除低优先级消息，保留计划类内容
参数写入config.toml保留原生max_message_count=100不修改
验证方式：执行超过 100 轮工具调用的长任务，检查任务原始计划消息是否保留在上下文中
建议 5：异常自愈链路绑定已有监控告警工具链
改进点：Agent 进入 error 自愈分支时自动串联调用存量工具usage_monitor、status_monitor、notify_feishu，上报故障类型、当前模型配额、任务编号，完整复用现有监控资产，不新增独立告警代码。
文件路径 D:\360Downloads\金庸\一念永恒\一念永恒小说\开源拉取\OpenManus\manus\agent\base.py，捕获异常自愈代码块中追加工具调用逻辑
上报字段：任务 ID、错误类型、当前使用模型、剩余额度
验证方式：主动制造超时异常，自愈完成后检查飞书是否收到完整故障监控消息
建议 6：增加状态变更日志持久化，生成审计 TXT 运行日志
改进点：每一次 idle/running/finished/error 状态跳转，追加写入时序日志文件，和项目现有的实时日志体系对齐，适配实时日志驱动调试法。
在 base.py 状态上下文管理器写入日志到./run_log/agent_state_trace_{task_id}.txt
验证方式：执行完整任务，打开日志核对全部状态流转记录
优先级：P2（远期）
我认为这个方案中最有价值的部分
四态状态机 + 上下文管理器保证状态一致性，作为整个远程监控、自愈系统的底层骨架，完美适配飞书远程管控的架构；
PlanningFlow 分步进度标记机制，天然适配金庸小说分章节跑批任务的分段管理；
ReAct 思考执行分离模型，契合我们设定的「MainAgent 只监督改代码，底层 Agent 执行跑批」的分工规范；
原生卡住自动干预机制，是实现无人值守长时间批量任务运行的基础自愈组件。
