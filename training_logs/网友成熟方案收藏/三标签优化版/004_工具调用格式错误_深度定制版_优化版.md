## 原始方案核心内容

### 一、工具调用格式错误的常见类型
1. tool_calls为None但content也为空
2. tool_calls中的function.name不存在
3. function.arguments不是合法JSON
4. 参数类型错误（如应该传int但传了str）
5. 缺少必填参数

### 二、根本原因
- 模型对工具schema理解不准确
- 系统提示词没有明确说明工具调用格式
- 上下文过长导致模型"忘记"工具格式
- 模型本身工具调用能力不足（小模型尤其明显）

### 三、解决方案
1. 系统提示词中明确说明工具调用格式和示例
2. 工具description写得非常详细，包含参数说明和使用示例
3. 错误处理：格式错误时返回明确的错误信息，让模型修正
4. 降级策略：连续3次格式错误后，切换到更强大的模型
5. 工具调用示例：在系统提示词中加入1-2个完整的工具调用示例

### 千问国际版的建议

你好！我是千问国际版。很高兴能参与到"OpenManus统帅方案深度优化"项目中。针对你提供的第2/3部分方案（工具调用格式错误深度定制版），我进行了深度分析。
原方案在解决工具调用格式错误方面思路清晰，但在上下文管理、并发执行安全、以及异常自愈方面存在一些潜在风险。以下是我的分析和改进建议。
我发现的问题（风险与Bug）
问题1：模型“降级”（实为升级）带来的上下文污染与丢失风险
问题2：批量工具调用的并发写冲突风险
方案建议“明确告诉模型可以一次调用多个工具”。但在我们的实际跑批场景中，如果模型同时调用两个 python_execute 或 batch_run 去修改同一个小说章节文件，会导致文件锁冲突、内容覆盖或IO异常，直接导致跑批崩溃。
问题3：错误反馈示例可能污染模型上下文
方案建议返回“正确的参数应该是什么样的”示例。如果错误示例和正确示例在文本中混合，模型可能会产生“模仿偏差”，在后续调用中错误地模仿了之前的错误格式。

问题1：修改核心解析代码缺乏“防崩溃”与“自愈”机制。 针对“工具调用格式错误”修改的代码通常位于LLM响应解析层（如 toolcall.py 或 base.py），属于系统中枢。原方案仅写“修改对应代码文件”和“语法验证”，没有强制备份和熔断回滚机制。如果统帅改坏了，会导致系统完全不可用，违背了可自愈原则。
问题2：“测试验证”缺乏针对“工具调用”的专属沙盒。 原方案的“明确的测试用例”过于抽象。验证工具调用格式是否修复，不需要跑全量小说任务，只需要一个极简的“强制触发工具调用”的Prompt测试即可，否则验证时间过长且浪费API额度。
问题3：未结合飞书形成远程闭环。 提取改进点和验证通过后，没有向飞书同步状态，不符合“通过飞书远程控制与监控”的核心目标。
我的改进建议（只做加法）
在原方案的【立即执行（P0）】、【后续执行（P1）】和【验证标准】清单中，追加以下具体内容：
建议1：P0阶段增加“改前自动备份与语法失败自愈”子步骤
改进点： 在修改解析代码前，利用已有的 python_execute 工具自动备份，语法验证失败时自动回滚，实现自愈。
具体修改：
在P0清单中追加：
- [ ] 修改文件前，调用 python_execute 执行 shutil.copy('目标文件.py', '目标文件.py.bak')
- [ ] 语法验证失败时，自动调用 python_execute 执行 shutil.move('目标文件.py.bak', '目标文件.py') 回滚，并通过 notify_feishu 发送告警
验证方式： 故意让统帅在解析代码中写入缩进错误，观察系统是否自动回滚原文件，且飞书“最强大脑”是否收到“语法错误已自愈”的告警。
优先级： P0（立即）
建议2：在【验证标准】中增加“极简工具调用沙盒测试”
改进点： 针对工具调用格式修复，定义一个不依赖长文本生成的极简测试用例，验证解析逻辑是否正常。
在【验证标准】清单中追加：
- [ ] 调用 status_monitor 查看该测试脚本的实时日志，确认无 JSON 解析报错（如 KeyError, JSONDecodeError）
验证方式： 统帅完成代码修改后，直接运行此沙盒测试。若飞书“最强大脑”收到“测试消息”，且日志无解析异常，即代表测试通过，无需跑小说章节。
建议3：P1阶段增加“验证结果飞书自动归档”机制
改进点： 将“记录到训练日志”和“记录到002文档”的动作自动化，并通过飞书同步状态。
在【后续执行（P1）】和【验证标准】中追加：
- [ ] 沙盒测试通过后，调用 python_execute 以追加模式(mode='a')将修改记录写入 002_完整版调试方案.md
验证方式： 测试跑完后，检查 002_完整版调试方案.md 底部是否有新记录，且飞书群是否收到成功通报。
优先级： P1（近期）
我认为这个方案中最有价值的部分
“提取最关键的1-2个改进点”的小步快跑策略。 针对工具调用这种核心逻辑的修改，最忌讳大刀阔斧。原方案要求只提取1-2个点，这种克制和聚焦是系统稳定性的基石，我们保留其骨架，用自动化工具将其填满即可。
