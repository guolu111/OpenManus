# 008_LLM集成最佳实践_深度定制版 - 千问国际版的改进建议

> 生成时间: 2026-09-05 23:36:22
> 处理部分: 第2/3部分

我发现的问题（如果有）
问题1：任务级模型选择的“分类器”套娃风险。原方案提出“根据任务复杂度自动选择模型”，如果用LLM来判断复杂度，本身就会消耗Token和增加延迟（形成死循环）；如果用简单规则，又无法准确评估“架构设计”等复杂任务。
问题2：工具结果摘要的“致命信息丢失”。原方案规定“超过500字的工具结果先用智谱4.0摘要”。如果工具返回的是关键代码、精确的JSON数据或长串数字，摘要极易丢失关键细节，导致后续Agent执行时产生严重幻觉。
问题3：备用大脑切换的“工具调用格式不兼容”。从谷歌中转API切换到智谱4.5-air时，两者的Function Calling（工具调用）格式和System Prompt解析能力可能存在差异。直接热切换可能导致Agent“不认识”工具或输出格式错误而崩溃。
问题4：流式响应（Stream）与工具调用的“解析冲突”。OpenManus原生依赖完整的JSON响应来解析工具调用。如果全局开启stream，需要自己实现流式JSON解析，极易因网络抖动导致JSON截断、解析失败，破坏现有的稳定性。
问题5：硅基9B“粗活专用”的上下文割裂。如果主Agent用谷歌，粗活切给硅基9B，硅基9B没有主Agent的完整上下文（如当前跑批进度、历史报错），直接让它做日志摘要或数据搬运，很容易“干错活”。

def get_llm_for_task(self, tool_name: str = None, task_desc: str = ""):
if tool_name and tool_name in TOOL_MODEL_ROUTING:
return self.load_llm(TOOL_MODEL_ROUTING[tool_name])
# 兜底：根据任务描述长度粗略判断
return self.load_llm("gemini-3.5-flash")

优先级：P0（立即）
建议2：工具结果摘要的“结构化数据保护区”
改进点：防止关键代码、JSON、精确数字在摘要中丢失，只对“纯文本描述”进行摘要。
具体修改：在 app/memory/token_optimizer.py 中，增加内容类型检测逻辑：
import re
def optimize_tool_result(self, tool_result: str) -> str:
if len(tool_result) <= 500:
return tool_result
# 保护区：如果包含代码块、JSON结构、长数字，坚决不摘要
if re.search(r'```|{|}|\[|\]|\d{5,}', tool_result):
# 不摘要，但如果超长则截断尾部，保留头部关键信息

建议3：备用大脑切换的“Prompt与工具格式适配器”
改进点：确保切换到智谱4.5-air时，工具调用格式和系统提示词能无缝兼容，防止Agent“失忆”或工具调用失败。
具体修改：在 app/llm.py 中，不直接替换底层模型，而是增加一个 LLMAdapter 包装层。当切换到智谱时，动态注入兼容提示词：
# 在 app/llm.py 的模型切换逻辑中
if target_model == "zhipu-4.5-air":
# 1. 转换工具格式（如果原生OpenManus不兼容智谱格式）
self.tools = self.convert_tools_to_zhipu_format(self.tools)
# 2. 在System Prompt末尾追加智谱专属指令
self.system_prompt += zhipu_hint
验证方式：手动将谷歌API额度耗尽（或在代码中Mock触发限额），观察系统切换到智谱4.5-air后，能否正常识别并成功调用 status_monitor 工具。
优先级：P1（近期）
建议4：流式响应的“分阶段降级保护”
改进点：防止流式解析JSON失败导致Agent卡死，确保工具调用阶段的绝对稳定。
具体修改：在 app/llm.py 的 ask_tool 和 ask_with_images 方法中，强制关闭流式；仅在纯文本生成（如最终回复）时开启流式。并增加解析失败的自动重试机制：
# 在 app/llm.py 的 ask_tool 方法中

建议5：模型性能监控的“自动熔断”与“飞书日报”
改进点：让监控数据直接服务于自动化决策，而不是仅仅生成静态报告。实现“劣币自动驱逐”。
具体修改：在 scripts/model_performance_report.py 中，增加“自动熔断”逻辑和飞书推送：
# 在 model_performance_report.py 中
def check_and_fuse_models(self):
for model_name, stats in self.model_stats.items():
# 如果连续3次超时，或错误率>50%，自动熔断
if stats['consecutive_timeouts'] >= 3 or stats['error_rate'] > 0.5:
self.disable_model_in_config(model_name) # 修改config.toml权重为0
# 调用飞书通知

def send_daily_report(self):
report_text = self.generate_report_text()
asyncio.run(notify_feishu(report_text))
验证方式：Mock某个模型连续3次返回超时，观察系统是否自动将其在配置中的权重降为0，并立即在飞书群收到“模型熔断告警”。
我认为这个方案中最有价值的部分
多模型分层调度（lite/3.5/pro/三标签）的构想：这是实现“成本与效果极致平衡”的核心。将好钢用在刀刃上，简单任务用免费/廉价模型，复杂任务用高级模型，完美契合我们“1200万智谱额度+谷歌三模型轮转”的资产现状。
引入免费/廉价模型处理“粗活”的思路：将智谱4.0和硅基9B专门用于日志摘要、数据搬运，是极致压缩Token成本的优秀工程实践，能大幅降低长周期跑批的整体开销。
Token优化前置到记忆层：通过“工具结果摘要”和“历史消息压缩”，从根源上解决了长上下文导致的Token爆炸问题。这不仅省钱，更能让模型在有限的Context Window内保持更高的注意力，提升跑批准确率。
