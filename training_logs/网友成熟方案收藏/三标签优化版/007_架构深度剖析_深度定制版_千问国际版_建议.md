# 007_架构深度剖析_深度定制版 - 千问国际版的改进建议

我发现的问题（如果有）
问题1：状态持久化的“半写”损坏与子进程失联风险。原方案提到将状态写入 agent_state.json，但如果进程在写入中途崩溃，会导致JSON文件损坏（半写状态），下次启动时无法解析。此外，如果Agent正在执行 batch_run 异步子进程时崩溃，仅恢复Agent状态不够，还需要知道子进程的PID和心跳，否则恢复后会产生僵尸进程或重复跑批。
问题2：记忆增强可能误删“核心指令”。原方案提到“替换早期消息”来实现任务摘要，这极易误删 System Prompt（系统提示）和 User 的初始 Task（任务指令），导致Agent在后期“忘记”自己是谁、要干什么。
问题3：跑批长任务会被 step_timeout 误杀。原方案已修复 base.py 添加 step_timeout=120秒，但 batch_run 跑批任务（尤其是大章节）执行时间可能远超120秒。如果不做特殊处理，Agent会在等待结果时因超时而强行中断任务。
问题4：卡住恢复“换模型”时的上下文爆炸。第2次卡住自动切换更强大的模型时，如果直接把当前完整的长上下文传给新模型，可能会因为Token超限或上下文干扰，导致新模型“秒卡”。
问题5：状态监控API增加运维复杂度。原方案提出提供HTTP接口，如果单独起一个HTTP服务，会增加端口和进程管理的负担，且与现有的飞书控制（feishu_relay_v1.py）割裂。
我的改进建议（只做加法）
建议1：状态持久化的“原子写入”与“子进程接管”机制
改进点：防止JSON文件损坏，确保进程崩溃重启后能正确接管正在运行的 batch_run 子进程。

建议3：跑批长任务的“超时豁免”与“心跳保活”
改进点：防止 batch_run 等长耗时工具被 base.py 的 120秒 step_timeout 误杀。

TIMEOUT_EXEMPT_TOOLS = ["batch_run", "python_execute"]
async def step(self):
# ... 获取 tool_name ...
original_timeout = self.step_timeout
if tool_name in TIMEOUT_EXEMPT_TOOLS:
self.step_timeout = 600  # 动态延长至10分钟
try:
result = await self.execute_tool(tool_name, tool_args)
finally:

建议5：状态监控API与飞书控制的“轻量级融合”
改进点：避免额外部署独立的HTTP服务，直接复用现有飞书通道，同时保留HTTP接口供未来看板使用。
飞书融合（主）：在 feishu_relay_v1.py 中增加对“查状态”指令的解析。收到指令后，直接读取 logs/agent_state.json，格式化为文本后通过“最强大脑”发回飞书。
HTTP接口（辅）：在 multi_bridge.py（端口8010）中，使用 FastAPI 增加一个轻量级路由：

验证方式：在飞书群发送“查状态”，能在3秒内收到当前Agent状态、正在执行的工具、已用Token等格式化信息；同时访问 http://localhost:8010/agent_status 能返回相同的JSON数据。
我认为这个方案中最有价值的部分
卡住恢复的分级策略（1次加Prompt，2次换模型，3次摇人）：这是实现“无人值守”最核心的设计。它将原本非黑即白的“超时失败”变成了渐进式的“自我救赎”，极大提升了长周期跑批任务的成功率。
记忆增强与 PlanningFlow 的结合：金庸小说跑批是一个典型的长上下文、多步骤任务。通过任务摘要防止上下文爆炸，通过 PlanningFlow 拆解子任务，使 Agent 具备了处理“天级别”复杂任务的架构基础。
跑批专用流程的深度绑定：将 status_monitor -> batch_run -> notify_feishu 固化为专属流程，而不是让 Agent 每次自由发挥去调用工具。这体现了“MainAgent只做监督，执行层高度标准化”的优秀工程思想，大幅降低了 LLM 幻觉导致的流程跑偏风险。
