# 009_工具调用系统开发指南_深度定制版 - 智谱清言的改进建议

我发现的问题（如果有）
问题0（元问题，第三次确认）：009的第3/3部分仍是同一套执行清单模板。 我在008分析中已给出模板级修复方案（建立《执行标准附录.md》共享文档）。如果那份附录还没落地，009就是第三个触发点——本回答中不再重复展开回滚、熔断等通用问题（问题：无快照、验证不可执行、无失败路径、记录去向不一致），统一引用附录方案，只讲009特有的新风险。
问题1（009特有，爆炸半径最大的一次）：工具系统改动触碰的是28个工具的共享地基。 “工具调用系统开发指南”的改动对象通常是 base.py（你们已改过step_timeout=120）、工具集合/注册文件（如app\tool\collection.py或统帅的加载处）、单个工具文件。前两类是全部28个工具共用的基础设施——base.py改坏一行，28个工具同时瘫痪，比007（单点改动）和008（LLM配置）的爆炸半径都大。
问题2（009特有）：工具故障是“静默”的，语法验证根本查不出来。 工具的parameters schema写错、description写得让LLM看不懂、参数名与实际execute签名不一致——这些全都不报错，后果只是“LLM不调用这个工具”或“调用时传错参数”。这属于“语法正确但功能已坏”的典型，方案的四条验证标准没有一条能抓住它。
问题3（009特有）：“测试验证”可能触发真实副作用。 你们28个工具里batch_run会启动真实跑批子进程、notify_feishu会发真实飞书消息。测试一个新改的工具如果没有干跑（dry-run）保护，可能真的往“最强大脑”刷屏、真的启动一轮章节跑批烧掉谷歌配额。
问题4（009特有）：新工具若用raise抛异常，会打断统帅主循环。 你们已给base.py加了step_timeout，但异常处理是另一回事——工具内部抛异常若不被捕获，整个agent步骤中断。工具开发指南必须规定“错误以字符串返回，不抛异常”。
我的改进建议（只做加法）
建议1：P0清单末尾追加附录引用行——模板级修复落地
改进点：把008建议1的《执行标准附录.md》（五条固定规则：快照→py_compile/tomllib验证→smoke_test门槛→失败熔断→002记录模板）应用到009，一次修复不再重复。
具体修改：009方案P0清单末尾追加一条：- [ ] 全程按 docs\执行标准附录.md 执行（附录尚不存在则P0第一项先创建它）。
验证方式：009的P0执行记录中出现附录引用及五条规则的逐项勾选。
优先级：P0
建议2：新增tools_check.py——“28个工具一个不少”的清点哨兵
改进点：针对问题1，工具系统任何改动后，必须验证全部工具仍能加载。这是009场景下smoke_test的核心补充项。
具体修改：在执行层目录新增 tools_check.py：
python
# tools_check.py 核心逻辑
import json, asyncio, sys
BASELINE = r"...\执行层\tools_baseline.json"
# 第一次运行前生成基线：遍历统帅的可用工具集合，导出全部工具名
async def main():
names = sorted(统帅工具集合的工具名列表)  # 通过加载tool collection获取
baseline = json.load(open(BASELINE, encoding="utf-8"))
missing = set(baseline["tools"]) - set(names)
assert not missing, f"工具丢失: {missing}"   # 共享地基被改坏的信号
added = set(names) - set(baseline["tools"])
print(f"PASS | 基线{len(baseline['tools'])}个 | 新增{added or '无'}")
asyncio.run(main())
基线文件初始内容为现有28个工具名。新增工具属正常演化，需显式更新baseline并加注释 "28→29: 新增file_snapshot"——防止“工具悄悄消失”被误当成正常。
验证方式：在沙箱副本中临时注释掉一个工具的注册→tools_check必须报“工具丢失”；恢复后PASS。
建议3：快照范围明确为“三件套”——工具改动标准保护范围
改进点：工具系统改动的波及文件固定，快照漏一个就留死角，尤其base.py是最高危共享文件。
具体修改：009方案“修改对应代码文件”前追加一条：- [ ] 对 base.py、工具集合/注册文件、被改工具文件 三者执行file_snapshot快照（复用007建议1已建的file_snapshot工具）。三者哪怕本次只改一个，也建议全拍——因为排查问题时经常发现真正的病灶在没改的那两个里，有快照就能对照“改动前”状态。
验证方式：回滚演练——改坏base.py→用.bak覆盖→tools_check与smoke_test全绿。
建议4：工具测试“双轨制”+dry_run约定——免费、确定、无副作用
改进点：针对问题3和配额保护，规定工具测试的两种合法方式。
具体修改：在009方案“测试验证”条目下追加两条规则：
主轨·直调测试（零token成本）：新/改工具先用python_execute直接调用其execute方法传测试参数，不走LLM循环——确定性强、不耗配额、能精确断言返回值。示例：result = await tool_collection.get_tool("usage_monitor").execute()，断言返回含“配额”字样。
副轨·真调测试（限免费模型一次）：直调通过后，用glm-4-flash让统帅真实调用该工具一次，验证schema/description能引导LLM正确选工具传参数（见建议7）。
副作用工具dry_run约定：batch_run、notify_feishu等有真实副作用的工具，测试时必须传 dry_run=True 参数。给这类工具统一加参数（加法）：
parameters = {..., "dry_run": {"type": "boolean", "description": "true时只校验参数并返回预览，不执行真实动作"}}
# execute开头：if dry_run: return f"[DRY-RUN] 将执行: {参数摘要}，未真实执行"
验证方式：对notify_feishu传dry_run=True调用→飞书不收到消息但工具返回预览文本；去掉dry_run才真收到。
建议5：追加“新工具开发五条军规”——写进009方案末尾
改进点：针对问题4，把工具开发的硬性规范固化，统帅以后每次写新工具都照此执行，避免每次重蹈覆辙。
具体修改：009方案末尾追加一节：
继承BaseTool，name用小写下划线，不与现有28个重名（重名会静默覆盖旧工具——tools_check的新增项比对也能兜底）；
execute一律async，内部整体try/except，错误以字符串返回（return f"ERROR: {e}"），禁止raise穿透；
耗时操作感知step_timeout=120秒，超过的操作改用子进程或分步；
parameters schema每个字段带description和示例值（description是给LLM看的，不是给人看的）；
完成后按顺序走：py_compile→tools_check→直调测试→更新tools_baseline→002记录。
验证方式：写一个故意违反军规2的工具（execute里raise）→在测试环境确认统帅步骤会中断；改为return错误串后确认统帅能读到错误并继续。
优先级：P1
建议6：LLM真调端到端验证——专治“静默schema故障”
改进点：问题2的静默故障只有一种方法能查出：让LLM真调一次。description写得好不好，LLM的选择就是唯一裁判。
具体修改：P1清单后追加：“工具类改动合入后，用glm-4-flash向统帅发一条自然语言指令（如‘查一下当前用量’），核验三点：①选中的是预期工具；②参数解析正确；③dry_run保护生效。任一不符即说明description/schema需要改，属于FAIL——即使工具直调全绿。”
验证方式：故意把某工具description改成与功能无关的话→真调测试应出现“选错工具/拒答”，修复后恢复正确选择。
建议7：002记录模板追加“工具台账”字段
改进点：009的改动都围绕工具，002应沉淀工具演化史，与建议2的baseline形成双账本。
具体修改：在008建议6的模板基础上追加三字段：- 工具变动: 新增X个/修改X个（列名）/基线28→N、- 直调测试: PASS/FAIL、- 真调测试: 选中工具正确/错误。写入方式不变：python_execute以 open(路径,"a",encoding="utf-8") 自动追加。
验证方式：009首个P0完成后，002末尾块的工具字段与tools_check输出一致。
我认为这个方案中最有价值的部分
“提取1-2个改进点”的克制对工具开发尤其关键：工具是统帅的手脚，一次改多个工具出问题时，LLM行为、schema、代码逻辑三层因素缠在一起，归因成本极高。小步+快照（建议3）是工具调参期唯一可靠的节奏。
“改进点有明确的测试用例”这条标准在009场景含金量最高：因为工具的故障模式（静默schema错误）恰恰是最依赖好测试用例才能暴露的。建议2/4/6把这一条扩成了直调+清点+真调三层防线，让口号有了牙齿。
写入002的知识闭环：对工具系统来说，002积累的将是一份“工具演化史+踩坑记录”——将来统帅写第29、第30个工具时，翻002就能避开历史上犯过的所有schema和异常处理错误，这是“训练日志”这个原始设想的真正价值所在。
同构清单的复利：007/008/009三份同模板清单，让“执行标准附录+tools_check+smoke_test+file_snapshot”这套基础设施只需建一次就覆盖全部方案——模板的重复性看似枯燥，实则是整个方案体系里自动化收益最高的杠杆点。
