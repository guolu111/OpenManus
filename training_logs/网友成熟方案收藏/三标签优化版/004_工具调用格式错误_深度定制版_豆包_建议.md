# 004_工具调用格式错误_深度定制版 - 豆包的改进建议

> 生成时间: 2026-09-05 21:26:18
> 处理部分: 第1/3部分

问题 1：原生降级逻辑仅支持 API 模型切换，没有对接现有multi_bridge.py:8010网页浏览器兜底链路，API 额度耗尽时系统没有自愈备选通道，跑批任务直接中断。
问题 2：重试计数器驻留内存，进程重启、任务中断后错误次数清零，连续 3 次失败的判定不可靠，降级触发逻辑失效。
问题 3：全部格式错误共用一套告警逻辑，无法区分轻微格式瑕疵与致命故障，notify_feishu无法实现分级推送，监控颗粒度过粗。
问题 4：没有落地坏报文持久存储机制，金庸长篇跑批产生的错误样本无法留存复盘，不能沉淀成 prompt 优化素材。
问题 5：缺少全局最大重试硬限制，存在无限循环重试、无谓消耗 API 额度的风险，会占用智谱、谷歌中转的可用次数。
问题 6：原始方案没有对接usage_monitor、status_monitor两个自研监控工具，工具调用异常不会写入全局用量与任务状态面板。
我的改进建议（只做加法）
建议 1：会话级错误计数持久化保存，进程重启不丢失状态
改进点：增加 JSON 缓存文件记录每一个会话的报错次数、报错类型与时间戳，内存变量仅作为运行缓存，持久文件作为权威数据源。
