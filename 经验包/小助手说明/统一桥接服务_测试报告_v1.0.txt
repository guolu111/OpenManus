================================================================================

【架构图】
                    ┌─────────────────────────┐

                    └───────────┬─────────────┘
                                │
          ┌──────────┬─────────┼─────────┬──────────┐
          ▼          ▼         ▼         ▼          ▼
      [标签页1]  [标签页2]  [标签页3]  [标签页4]  [标签页5]
      DeepSeek   hanbaoyu    千问       Kimi      智谱清言
      deep-web   hanbaoyu-  qwen-web   kimi-web  glm-web
                 web

【关键设计】
1. 统一profile：web_cache/unified_profile
   - 从5个旧profile迁移cookies+localStorage，无需重新登录
   - 不同平台cookie按域名自动隔离，互不干扰

2. 独立请求锁：每个标签页有独立的asyncio.Lock
   - 同一平台串行处理（网页版天然串行）
   - 不同平台可并行处理（5个标签页独立）

3. 模型路由：根据请求的model字段分发到对应标签页
   - deep-web → DeepSeek标签页
   - hanbaoyu-web → hanbaoyu标签页
   - qwen-web → 千问标签页
   - kimi-web → Kimi标签页
   - glm-web → 智谱清言标签页

4. 内存对比：
   - 旧方案：5个独立Chrome进程 ≈ 1.5-2.5GB
   - 新方案：1个Chrome + 5个标签页 ≈ 400-600MB
   - 节省约70%内存

三、各通道技术实现细节
================================================================================

【1. DeepSeek (deep-web)】
- 网址：https://chat.deepseek.com
- 输入：textarea（第一个），fill + Enter
- 输出：.ds-markdown 最后一个元素的inner_text，DOM轮询（稳定3次）
- 特殊：角色扮演包装（HEADER+FOOTER），组装对话历史为"继续角色扮演"格式
- 速度：慢（约20-60秒/条），适合少量重要任务
- 旧profile：D:\bat\py\本地api\cache
- 迁移数据：5 cookies + 32项localStorage

【2. hanbaoyu (hanbaoyu-web)】
- 网址：https://hanbaoyu.ggff.net/login（仅用于建立浏览器会话过Cloudflare）
- 输入：无输入框，直接在page上下文内fetch上游API
- 输出：fetch返回的JSON（OpenAI兼容格式）
- 特殊：Cloudflare只放行真浏览器TLS，普通HTTP客户端被重置；用浏览器内fetch绕过
- 上游端点：https://hanbaoyu.ggff.net/v1（从hanbaoyu_config.json读取）
- 额度：平台每日FLASH额度（与凭证上游余量无关），明日重置
- 旧profile：中转API/hanbaoyu_cache
- 迁移数据：1 cookies

【3. 千问 (qwen-web)】
- 网址：https://chat.qwen.ai/
- 输入：textarea.message-input-textarea，原生value setter设值（不click）+ Enter
  - 为什么不用fill/keyboard.type：千问React受控组件+IME拦截，fill会导致中文变问号
  - 原生setter方案：Object.getOwnPropertyDescriptor(HTMLTextAreaElement.prototype,'value').set
  - 带3次校验重试，确保输入正确
- 输出：SSE拦截模式（page.expect_response拦截/api/v2/chat/completions）
  - 解析SSE的delta.content增量，phase="answer"为最终回复，phase="thinking_summary"为思考摘要（忽略）
  - 比DOM轮询更快更稳定
- 速度：最快（约13-20秒/条）
- 旧profile：中转API/web_cache/qwen_profile
- 迁移数据：31 cookies + 20项localStorage

【4. Kimi (kimi-web)】
- 网址：https://www.kimi.com/
- 输入：div.chat-input-editor（contenteditable div），execCommand('insertText') + Enter
  - 为什么不用fill：contenteditable不是textarea，fill不生效
  - 为什么不用textContent：React受控组件，直接设textContent不触发onChange
  - execCommand方案：focus → selectAll → insertText，触发真实input事件
- 输出：多选择器DOM轮询（.message-content/.markdown-body/.response-content等）
- 速度：中等（约19-30秒/条）
- 旧profile：中转API/web_cache/kimi_profile
- 迁移数据：8 cookies + 39项localStorage

【5. 智谱清言 (glm-web)】
- 网址：https://chatglm.cn/（必须用主页，自动重定向；不能直接访问alltoolsdetail）
- 输入：textarea.scroll-display-none，click + fill + Enter
- 输出：多选择器DOM轮询，优先取.answer-content/.answer（最终回复），排除思考过程
  - 思考过程特征：含"用户要求"/"思考中"/"思考过程"，必须排除
  - 否则会取到思考过程导致稳定性检测永远不通过、180秒超时
- 速度：中等（约18-30秒/条）
- 旧profile：中转API/web_cache/glm_profile
- 迁移数据：10 cookies + 24项localStorage

四、脚本文件清单与功能说明
================================================================================

【统一服务核心脚本】
1. web_bridge_unified.py
   - 功能：5网页桥接统一服务主程序
   - 端口：8010
   - 用法：python web_bridge_unified.py（启动服务）
   -       python web_bridge_unified.py --test qwen（测试指定通道）
   - 模型：deep-web / hanbaoyu-web / qwen-web / kimi-web / glm-web
   - 端点：GET /v1/models、GET /v1/status、POST /v1/chat/completions

2. migrate_profiles.py
   - 功能：从5个旧profile导出cookies+localStorage，迁移到统一profile
   - 用法：python migrate_profiles.py（一次性操作，迁移后无需再运行）
   - 导出目录：web_cache/_migrate_export/（迁移后可删除）
   - 备份：迁移前自动备份旧统一profile到unified_profile_bak

3. start_unified_login.py
   - 功能：5平台统一登录脚本（备用，迁移失败时使用）
   - 用法：python start_unified_login.py（弹出Chrome，5个标签页登录，完成后按Enter）
   - 注意：迁移成功后无需使用此脚本

【旧独立桥接脚本（保留备用，统一服务启动后可不再运行）】
4. qwen_bridge.py — 千问独立桥接（端口8003，SSE拦截模式）
5. kimi_bridge.py — Kimi独立桥接（端口8004，DOM轮询）
6. glm_bridge.py — 智谱清言独立桥接（端口8005，DOM轮询）
7. hanbaoyu_bridge.py — hanbaoyu独立桥接（端口8002，fetch代理）
8. start_deepseek.py / stop_deepseek.py — DeepSeek独立桥接启停（端口8001）
9. start_hanbaoyu.py / stop_hanbaoyu.py — hanbaoyu独立桥接启停

【管理与调用脚本】
10. web_bridge_manager.py — 旧三桥接统一管理（start/stop/status/test，端口8003-8005）
11. web_helper.py — 网页桥接统一调用模块（被batch_run.py import，直接HTTP调用）

【查看服务状态】
浏览器访问 http://127.0.0.1:8010/v1/status
（返回各平台标签页URL和就绪状态）

【OpenAI兼容调用】
curl -X POST http://127.0.0.1:8010/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen-web","messages":[{"role":"user","content":"你好"}]}'

【Python调用】
import urllib.request, json
url = "http://127.0.0.1:8010/v1/chat/completions"
payload = json.dumps({"model":"kimi-web","messages":[{"role":"user","content":"你好"}]}).encode("utf-8")
req = urllib.request.Request(url, data=payload, headers={"Content-Type":"application/json"})
with urllib.request.urlopen(req, timeout=180) as resp:
    data = json.loads(resp.read().decode("utf-8"))
    print(data["choices"][0]["message"]["content"])

【批量跑量】
python batch_run.py --agent all6 --input 任务清单.txt --out 结果/
（all6 = gcli + deep + hanbaoyu + qwen + kimi + glm 六通道均分）
（web = qwen + kimi + glm 三网页通道均分）

【重要注意事项】
1. 统一服务启动后，旧的独立桥接（端口8001-8005）可不再启动，避免重复占用资源
2. 同一平台串行处理（网页版天然串行），不同平台可并行
3. 千问通道最快（SSE拦截），DeepSeek最慢（角色扮演包装+DOM轮询）
4. hanbaoyu有每日FLASH额度限制，用完返回429，明日重置
5. 登录态保存在统一profile，浏览器关闭后不丢失；如登录态过期，重新运行migrate_profiles.py或start_unified_login.py

六、与旧方案对比
================================================================================

维度          | 旧方案（5独立Chrome）        | 新方案（1Chrome+5标签页）
--------------|------------------------------|---------------------------
内存占用      | ~1.5-2.5GB                   | ~400-600MB
启动时间      | 5×20秒=100秒（逐个启动）     | ~20秒（一次启动5标签页）
并行能力      | 5进程并行，但资源竞争严重     | 5标签页并行，资源竞争小
三通道并行    | 千问超时（资源不足）          | 5通道可同时处理
管理复杂度    | 5个服务分别启停               | 1个服务统一管理
登录态        | 5个独立profile                | 1个统一profile
端口          | 8001/8002/8003/8004/8005    | 8010（统一）
故障隔离      | 一个崩溃不影响其他            | 浏览器崩溃全部受影响（但有自动恢复）

七、已知问题与后续优化
================================================================================

【已知问题】
1. hanbaoyu页面导航偶发ERR_QUIC_PROTOCOL_ERROR（Cloudflare QUIC协议），但fetch代理仍正常工作
2. DeepSeek回复较短（角色扮演包装可能影响回复质量），可考虑去掉包装或调整提示词
3. 智谱清言回复中包含"思考结束"标记（思考过程未完全排除），可优化选择器

【后续优化方向】
1. Kimi和智谱清言升级为SSE拦截模式（参考千问v2），进一步提速
2. 5通道并行压力测试，确认低配电脑的最大并行数
3. 自动恢复机制：浏览器崩溃后自动重启并恢复5个标签页
4. 统一服务集成到web_bridge_manager.py，统一管理启停
