一、这套流程是怎么运作的（架构全景）
--------------------------------------------------------------------------------
【目标】用"4标签网页版AI"（豆包/千问/Kimi/智谱清言）真实跑通鹿鼎记分天分析，
4主力在浏览器标签里真实问答，严禁角色扮演/冒充API自己跟自己跑。

【三层组件】
┌─────────────────────────────────────────────┐
│ 统帅层（用户触发）                            │
│   tongshuai_chat.py（智谱glm-4.6收费当统帅）  │
│   识别"跑第21章"→触发跑批                     │
├─────────────────────────────────────────────┤
│ 执行层（跑批脚本）                            │
│   ldj_4tag_batch.py：分天任务→4标签并行→     │
│   失败回池重试→校验→组装成果→谷歌验收         │
├─────────────────────────────────────────────┤
│ 支撑层（浏览器+桥接+守护）                    │
│   _browser.py（启动4标签Chrome）              │
│   multi_bridge.py（8010桥接，模拟人工问答）   │
│   _chrome_guard.py（守护，浏览器闪退自动拉起）│
└─────────────────────────────────────────────┘

【一次完整跑批的步骤】
1. 用户/统帅输入"跑第21章"
2. 换会话（复用优先：点旧会话LDJ-前缀，未满阈值不新建）
3. 健康检测（发测试消息，乱码/超时模型降级）
4. 分天并行分析（6天任务分给4标签，每天由1个标签回答）
5. 七行结构校验（标题/概述/情节开头/发展/转折/结尾悬念/断点评价）
6. 失败回池重试（最多3轮，避开该天已失败的模型）
7. 组装"每日分析成果.txt"（6天完整）
8. 谷歌中转验收（管理员2.5-flash-lite总验→世界书3.5-flash复核→Pro兜底）
9. 归档+台账登记（跑批归档+验收记录+gcli用量）

四、为什么成功/为什么失败（核心结论）
--------------------------------------------------------------------------------
【成功三要素】
1. 标签健康：4标签页面状态正常（换会话+健康检测通过）
2. 容错机制：失败回池重试能避开失败模型
3. 浏览器稳定：Chrome不闪退（chrome_guard守护生效）

【失败三主因】
1. 标签劣化：glm/kimi 长文本分析后页面DOM损坏→持续500（最致命）
2. 换会话超时：qwen旧会话定位慢，60s超时拖节奏
3. 原脚本无"连续失败踢出"：glm坏了还反复分配→每轮等160s+→死锁

六、4标签处理细节（重点）
--------------------------------------------------------------------------------
【标签生命周期】
启动：_browser.py --start → Chrome + 4标签（豆包/千问/Kimi/智谱）
换会话：每章开始 force_new_all → 复用旧会话(LDJ-前缀)优先，未满阈值不新建
        （豆包40次/千问40次/Kimi10次/智谱20次才换）
健康检测：发测试消息 → 乱码/超时降级
正式分析：6天任务并行，每标签1天
失败处理：七行结构校验不过→回池→换标签重试→连续3次失败踢出
劣化恢复：force_new刷新标签页（goto平台URL）

【标签劣化的识别与对策】
- 识别：健康检测OK但正式长文本500/超时 → 页面劣化
- 现状：force_new刷新不能稳定恢复（glm/doubao刷新后仍超时）
- 建议（待验证）：劣化标签可能需要用户手动在浏览器里操作/重新登录，
  或重启整个浏览器（_browser.py --stop --force + --start）
