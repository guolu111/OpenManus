四、联网搜索解答的问题
----------------------------------------------------------------------

【问题1：bridge为什么会崩溃？Chrome为什么会全灭？】
搜索关键词：playwright persistent_context 失败 浏览器进程被杀死 自愈
搜索结果：
- GitHub issue #35466（roger-rodriguez/playwright-persist-context-bug）确认这是
  playwright 持久化上下文的已知bug：headless实例无法干净关闭，留下 SingletonLock
  文件，可能损坏profile数据库，导致后续使用同一userDataDir启动失败。
- atanit技术博客分析：僵尸Chrome锁定userDataDir导致新会话无Cookie；
  launchPersistentContext 禁止同一userDataDir多重启动。
- 我们bridge的"最后手段：清理残留Chrome"逻辑会在launch失败时杀掉所有Chrome进程，
  这是导致浏览器全灭的直接原因——它本意是清理僵尸，但误杀了正常运行的浏览器。

【问题2：如何实现bridge的自我纠错/自愈？】
搜索结果提供了4个成熟方案：
1. Playwright Browser Manager MCP（lumoslnt）的 Auto-healing recovery 模式：
   浏览器意外关闭时，拆除陈旧子进程→重新启动→重试一次。还有Lazy launch
   （浏览器仅在首次使用时启动）和Session forking（登录一次后fork独立副本）。
2. playwright-mcp-server（doucej）的 ensureInitialized() 模式：
   每次调用前检查 browser.isConnected() 和 page.isClosed()，如果浏览器崩溃
   则重新启动并从最后持久化状态恢复。"The server never throws."
3. Markaicode 的错误边界模式：所有Playwright操作包裹在try/catch中，
   检测到崩溃先尝试恢复会话（从持久化profile），失败则回退到干净会话。
4. Runebook 的 Always-On 模式：定期轮询浏览器是否存活（不只是监听close事件），
   处理"静默断开"问题。

【问题3：bridge_guard守护为什么没恢复成功？】
分析：当前bridge_guard只检测8010端口并重启bridge进程，但Chrome全灭时
bridge启动会因launch_persistent_context失败而退出。需要增强守护逻辑：
检测到Chrome=0时，先启动浏览器（或清理SingletonLock），再启动bridge。

五、可行性建议（改进方向）
----------------------------------------------------------------------

【优先级1：修复bridge自杀逻辑（最紧急）】
- 移除或限制 multi_bridge.py / _browser.py 中"最后手段：清理残留Chrome"逻辑
- 改为：只清理与本bridge profile关联的Chrome进程（按--user-data-dir匹配），
  绝不杀全部Chrome
- 启动前检查并清理 SingletonLock 文件（playwright已知bug的标准解法）

【优先级2：实现ensureInitialized()自愈模式】
- 每次收到请求前检查 browser.isConnected()
- 断开则自动重启context+重连标签，不退出bridge进程
- 所有Playwright操作包裹错误边界，崩溃后自动重试1次

【优先级3：增强bridge_guard守护】
- 检测Chrome=0时，先清理SingletonLock→启动浏览器→再启动bridge
- 定期健康检查轮询（每30秒），不只是端口检测
- 记录自愈动作到 bridge_health.jsonl

【优先级4：air润色提示词增强】
- 增加"删除一切非七行标签的占位符（如xxx、XXX、--等），只输出标准七行"
- 增加"如果输入内容不含七行标签，自行根据内容生成标准七行结构"

【优先级5：标签500错误自动重试】
- 当前遇到500直接跳过，改为自动重试2次（间隔5秒），仍失败才跳过
- 减少补跑次数，提高全章一次成功率

【优先级6：跑批脚本增加--force参数】
- 支持强制重跑指定天（当前需手动删除results行才能重跑）
- 方便格式修正后的重跑

六、结论
----------------------------------------------------------------------
1. 四API+4标签协同跑批架构已验证可行：5章30天全部成功，API真实调用可追溯，
   air按额度统计、其他按次数统计，无角色扮演冒充。
2. gcli指挥官（谷歌中转）发挥了决策+验收作用，每章7~9次调用，智能度足够；
   智谱air润色净化杂质效果显著（8万token消耗，占1200万额度0.67%）；
   智谱free补齐机制在标签回复偏短时有效兜底；硅基9B轻量检查零失败。
3. 最大风险点是bridge的浏览器管理：自杀逻辑会误杀Chrome导致全灭。
   联网搜索已确认根因（playwright persistent_context已知bug）和成熟解法
   （ensureInitialized+错误边界+SingletonLock清理），建议按优先级1~3修复。
4. 参与度递减验证：第24/26章零介入，第25/27/28章各1次介入（均为补跑/格式修正），
   且介入方式以"脚本断点续跑"为主，未手动改数据。距离"最强大脑独立跑批"
   还差bridge自愈能力的完善——修复优先级1~3后可实现零介入连续跑批。
