一、现有架构优缺点分析
优点（≥3 条）
分层演进清晰，增量交付可控
采用四阶段迭代模式，从基础角色→角色增强单实例→多角色协同→远程操控逐层搭建，原有 Manus 核心能力完全复用，ManusWithRoles 使用继承方式做能力增强，旧代码无破坏性改动，符合项目小步验证、模拟先行再落地的开发节奏。
角色权限与调度模型已经固化成型
角色注册表、四阶权限、五维评分选择器、串行 / 并行 / 混合调度模式 + 三支中层指挥官业务域划分，形成一套可复用的 AI 团队协作范式；世界书动态台账（通气公告 / 决议 / 执行历史）沉淀了长流程任务记忆机制。
观测体系提前预留骨架
TaskDashboard 任务追踪、LogMonitor 日志告警骨架提前设计，天然支持「实时日志驱动调试法」的工程方法论，为自动化排障、跑批验收、bug 经验沉淀打下数据基础。
外部接入层解耦预留接口
FeishuHandler 独立封装消息解析、签名校验、指令翻译，业务调度和消息网关分离，后续可以低成本新增微信、本地 CMD 控制台等多种操控入口。
缺点（≥3 条）
顶层入口碎片化，调用链路不统一
业务调用分为两条独立分支：ManusWithRoles（单角色）、MultiRoleOrchestrator（多角色集群），外部调用方需要手动判断使用哪一个调度器，不存在统一对外门面；飞书处理器需要分别对接两套执行对象，增加上层逻辑判断成本。
全流程同步阻塞执行，无异步事件总线
当前执行链路是线性同步调用：消息解析→直接 run 执行→等待完整返回，任务一旦超时、卡住、模型重试、长时间跑批会阻塞飞书网关；无法实现后台静默执行、任务离线回调、多任务并发排队。
状态孤岛，三份独立数据源互不感知
RoleOrchestrator：角色激活 / 权限状态
TaskDashboard：任务优先级、执行进度、重试次数
LogMonitor：运行告警、异常事件
三者没有统一状态存储，任务失败时无法一键汇总「任务信息 + 角色快照 + 完整运行日志」，自动化复盘与经验包归档需要额外手工聚合文件。
配置分散，工程运维成本高
模型 / 密钥存放于 toml 配置，角色卡存放 txt 文本，世界书为独立文件；缺少统一配置中心，版本切换、环境隔离（开发 / 测试 / 生产）需要手动修改多份文件。
能力仅停留在内存模拟，边界实现缺失
飞书长连接、前端看板、告警推送、真实 API 路由、端到端多角色测试均为结构预留，没有消息队列、持久化存储、异步 worker 作为底层支撑，无法大规模跑批生产。
二、架构优化建议（P0 最高优先级 → P2 低优先级，共 6 条）
P0 = 必须优先落地，支撑现有功能工程化；P1 = 扩展增强；P2 = 长期迭代优化
P0：新增统一门面 Commander 统帅入口，封装两套执行器
不废弃 ManusWithRoles、MultiRoleOrchestrator，由 Commander 作为唯一对外调用门面，自动判断单角色 / 多角色协同路由；统一入参格式、统一返回结构、统一提交任务到状态中心，飞书 / 本地脚本后续只对接 Commander。
P0：引入轻量事件总线，改造为事件驱动架构，保留原有同步调用兼容模式
新增独立 EventBus 模块，支持两种运行模式：兼容原有同步模式 + 新增异步后台任务模式；任务启动、角色切换、异常报错、执行完成全部抛出事件，驱动看板更新、日志采集、告警触发，适配实时日志驱动调试法。
P0：构建全局统一状态中心 StateStore，消除状态孤岛
集中持久保存任务元数据、角色运行快照、执行历史、告警标签；TaskDashboard、RoleOrchestrator、LogMonitor 全部读写同一个状态数据源；跑完任务自动打包运行记录，写入经验包目录，自动归档蒸馏文档与世界书快照。
P1：重构统一配置管理层 ConfigHub
聚合 toml 模型配置、txt 角色卡、世界书文件；支持环境区分 (dev/test/prod)、动态重载角色卡，单独隔离模型轮转解析逻辑（遵循项目经验：模型轮转独立解析，不嵌入 llm 配置块）；配置变更自动触发事件通知统帅刷新角色注册表。
P1：完善异步 Worker 任务队列，落地真实飞书长连接
拆分网关与执行 worker：FeishuHandler 仅负责消息接收与指令提交给 Commander，真正的 AI 任务交给后台 Worker 异步执行；支持任务超时管控（最低 180 秒超时 + socket 底层超时双配置），隔离独立 Chrome bridge 实例，避免浏览器上下文抢占冲突。
P2：增加标准化集成测试流水线 + 自动化经验包蒸馏
增加端到端测试用例覆盖多角色完整协同链路；任务执行结束后自动打三标签 / 四标签跑批标记，自动提取 bug 日志、验收记录，更新本地经验包目录，自动蒸馏聊天记录补充世界书记忆。

五、事件驱动机制实现方案（轻量落地，避免重型中间件）
技术选型原则
初期不引入 RabbitMQ/Kafka 重型组件，内存事件总线 + 文件持久化事件日志实现最小可用版本；未来可无缝替换为消息队列。
EventBus 核心结构：发布订阅模式
subscribe(event_name, callback)：各个模块注册监听事件
publish(event_name, payload)：发布事件，携带结构化载荷（task_id、role_id、异常信息、时间戳）
预定义事件枚举（固定事件集合）
TaskSubmitted：任务提交
TaskStarted / TaskCompleted / TaskCancelled / TaskFailed
RoleActivated / RoleDeactivated
AlertRaised：告警触发
LogSnapshot：关键日志快照（适配实时日志驱动调试法）
模块订阅关系
TaskDashboard 订阅全部任务事件 → 更新任务进度
LogMonitor 订阅 AlertRaised、LogSnapshot → 聚合告警
ExperienceArchiver 订阅 TaskCompleted → 自动归档经验包
Commander 监听 TaskFailed，触发内置重试策略
双执行模式兼容
同步模式：事件顺序回调，等待完整执行结束（兼容现有 CMD 跑批脚本）
异步模式：交给后台 Worker 消费事件，网关立刻返回任务 ID，实现长任务离线运行
六、统一状态管理 StateStore 设计方案
设计目标
合并三份独立状态源，提供统一读写接口，数据持久化落地（JSON/Yaml 文件，后期可平滑迁移 sqlite），任务全链路快照可回溯复盘。
三大状态分区存储
Task 任务域
task_id，指令原文，优先级，创建时间，状态（pending/running/success/failed），重试次数，执行日志路径，结果快照
Role 运行域
绑定 task_id，激活角色列表，权限快照，世界书版本，本次任务决议台账快照
Alert 告警域
绑定 task_id，异常标签，报错日志片段，告警等级，是否推送通知
对外提供标准化方法
create_task_snapshot()：新建任务记录
update_task_state()：更新执行进度
get_full_context(task_id)：一次性获取【任务 + 角色 + 告警 + 日志路径】完整复盘包
archive_task(task_id)：导出归档文件存入经验包目录
和原有模块协作方式
RoleOrchestrator、TaskDashboard 不再独立维护内存状态；所有状态变更请求改为调用 StateStore，状态变更自动抛出事件，完全消除数据孤岛。
