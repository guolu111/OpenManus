- 目的：知道这个任务需要调用哪个业务角色卡（生成/分析/向量/匹配/学生/老师）

- 同时看幕进度记录（角色卡/运行记录/幕进度记录.txt），知道当前进度到哪一幕，从哪一幕继续，不会重复跑也不会漏跑
- 按幕模式：一次只跑一幕，不跑整章

【执行中：1步执行】

第六步：按幕执行任务
最小执行粒度不是"章"，是"幕"。
每一次只调用一个业务角色卡，处理一幕（3-5拍）。

执行前必须先定位本次任务的输入文件完整路径：
- 分析卡：输入是《第X章四幕十六拍》txt，必须给出完整路径
- 向量卡：输入是《第X章分析报告》txt，必须给出完整路径
- 匹配卡：输入是《第X章四层候选》json + 《第X章分析报告》txt，必须给出完整路径
每个输入文件必须给出完整路径，禁止写"见某文件夹"或"自己找"。

执行顺序：
1. 先确定本章四幕的幕号（第一幕/第二幕/第三幕/第四幕）
2. 从第一幕开始，一次只跑一幕
3. 每跑完一幕，立即执行"按幕检查流程"（见六·补）
4. 检查通过，才进入下一幕
5. 同一章四幕全部通过，才进入下一章
6. 同一角色卡的全部幕都完成后，才切换到下一个角色卡

禁止：
- 禁止一次跑一整章（16拍）
- 禁止一次跑多章
- 禁止一次调用多个角色卡
- 禁止"分析完8章再统一检查"

========================================
六·补：按幕检查流程（每幕必须执行）
========================================
每完成一幕（3-5拍），管理员卡必须立即检查，不能等整章跑完。

检查内容：
1. 这一幕包含的拍是否全部完成？
   - 少一个拍就不通过
2. 每拍的输出是否符合对应角色卡规则？
   - 分析卡：是否有四层分析+触发条件字段+原创词改写
   - 向量卡：是否输出四个独立候选集
   - 匹配卡：是否有行号+原文+主体检查+核心动作检查
3. 仿写检查（最高优先级）
   - 先检查原文是用脚本提取的，还是模型手写的
   - 如果提取过程没有脚本执行记录 → 直接判违规，该幕作废
   - 再抽查1-2拍，把"输出原文"和txt原行逐字对比
   - 不一致 → 该幕作废，重跑
4. 检查结果写进"幕进度记录.txt"

检查通过 → 记录✅，进入下一幕
检查失败 → 记录❌+原因，该幕重跑，不进入下一幕

【执行后：4步反刍（必须执行，不能跳过）】

第七步：反刍检查1——思考过程蒸馏
- 检查本次任务的思考过程是否经过蒸馏
- 把角色卡相关的关键信息蒸馏进：角色卡/角色卡蒸馏版.txt
- 把非角色卡相关的关键信息蒸馏进：角色卡/非角色卡蒸馏版.txt
- 蒸馏原则：只记"以后还会用到的关键信息"，不记完整过程

第八步：反刍检查2——项目记忆更新
- 把本次任务的关键信息蒸馏进：项目记忆_蒸馏版.txt（主目录）
- 包括：做了什么、重要决定、发现的坑、文件位置、下一步计划

第九步：反刍检查3——运行记录追加
- 在：角色卡/运行记录/角色卡运行记录_v1.0.txt 追加一条运行记录
- 记录格式见运行记录文件
- 必须包含反刍检查的6项结果

第十步：反刍检查4——角色卡和世界书是否需要调整
- 检查本次任务中，业务角色卡是否有需要微调的地方
- 检查通用世界书是否有需要补充的规则
- 如果需要调整，记录在运行记录的"问题与改进"栏
- 重大调整必须经过用户同意，小调整可以自主执行并记录

第十一步：更新目录索引（如有文件结构变更）
- 如果新增/删除/重命名了文件或文件夹，更新目录索引

======================================================================
一·补：角色卡执行强制校验流程（管理员卡最高优先级·v2.3新增）
======================================================================

【为什么要有这个流程】
第3章v6.3翻车的根因：角色卡没有严格按匹配卡v6.3执行，直接跳过"从txt按行号提取原文"，改用大模型凭记忆仿写金庸风格文本。角色卡文本写得再好，如果没有一个总控机制强制它"每一步对照卡执行"，下次还会跳。
所以本流程是管理员卡的最高优先级，任何业务角色卡执行时必须遵守。

========================================
一、执行前：列出"本任务必做步骤清单"
========================================
每次调用任一业务角色卡前，MainAgent必须先做一件事：
读取该角色卡全文，列出本次任务必须执行的步骤，形成"必做步骤清单"。

格式：
【必做步骤清单】
- 任务：第3章拍一主选提取
- 调用角色卡：匹配卡v6.4
- 必做步骤：
  1. 读取分析卡四层分析结果（不是重分析）
  2. 读取向量卡四层候选（不是凭记忆找）
  3. 按行号从txt提取原文（必须用脚本提取）
  4. 读完整原文≥500字
  5. 主体检查
  6. 核心动作检查
  7. 触发条件检查
  8. 选主选或判未找到

注意：
- 清单必须在执行前列出来，不能边做边想
- 清单里的每一步必须是该角色卡规则里明确要求的
- 如果角色卡规则里没有某一步，但本次任务需要，也要列出来并标注"额外步骤"

========================================
二、执行中：每一步留痕
========================================
每完成一个步骤，必须输出一行执行记录：
✅ 步骤1完成：已读取分析卡四层分析（文件名：XXX）
✅ 步骤2完成：已读取向量卡四层候选（文件路径：XXX）
✅ 步骤3完成：已用脚本从txt按行号提取原文（行号：XXX）

如果某一步被跳过，必须立即停止，写：
❌ 步骤X未执行，原因：XXX，本拍作废，重新从步骤1开始。

注意：
- 留痕不是形式主义，是强制自己确认每一步真的做了
- 特别是"从txt提取原文"这一步，必须留痕，不能凭记忆写
- 如果某一步执行失败（比如行号不对），必须记录失败原因，然后换方法重试，不能跳过

========================================
三、执行后：逐条对照铁律/禁止条款
========================================
完成一个拍后，最后输出一段"铁律自查"：

【铁律自查】
- 铁律一（读完整原文≥500字）：✅ 已读 / ❌ 未读
- 铁律二（主体检查+核心动作检查）：✅ 通过 / ❌ 未执行
- 铁律三（找不到写未找到，禁止硬贴）：✅ 执行 / ❌ 违规
- 最高铁律（原文从txt提取，禁止仿写）：✅ 原文从txt提取 / ❌ 疑为仿写

注意：
- 铁律自查必须在每个拍的最后输出，不能等全部拍完再统一写
- 如果任何一项是❌，该拍必须作废，重新从步骤1开始
- 不能"先标✅后面再改"，必须真的做了才能标✅

========================================
四、最高铁律：原文必须从txt提取
========================================
第3章v6.3犯的错，是用了仿写原文充当真原文。
因此本条是最高铁律，高于其他所有规则：

原文必须从本地txt文件按行号提取。禁止凭记忆写原文。
如果无法从txt提取，只能写"未找到"，绝对不允许写一段"像金庸风格"的文字。

违规识别方式：
把输出的"原文"和txt里对应行号的原文逐字对比。
不一致 → 判定违规，该拍作废，重新从步骤1开始。

========================================
五、管理员卡负责最终验收
========================================
任务全部完成后，管理员卡必须做一个总的执行验证：
1. 抽查每章至少3个拍，把"输出原文"和"txt原文"逐字核对
2. 如果发现1处仿写，整个章节作废，重跑
3. 验收通过后才允许更新项目记忆和运行记录

注意：
- 验收不是形式主义，是真的打开txt逐字对比
- 抽查的拍必须包含：通过率最高的拍、用户最关心的拍、之前出过问题的拍
- 如果验收发现仿写，必须记录在运行记录的"问题与改进"栏，并分析为什么跳步了

【按幕模式】

每幕完成后，管理员卡按"按幕检查流程"检查，通过才进入下一幕。
同一角色卡的全部幕都完成后，才切换到下一个角色卡。
禁止一次跑一整章（16拍），禁止一次跑多章，禁止一次调用多个角色卡。

【v6.5新流程核心原则】
1. 模式A优先：用户给了具体章节就用模式A，简单准确不会出错
2. 原文必须从txt用脚本提取，禁止凭记忆仿写
3. 模式A不做分析不做判断，用户指定什么就提取什么
4. 模式B是备选，倒过来匹配是漏斗不是打分表，每一层只排除不判定
5. 思想层筛选必须做"触发条件检查"
6. 正常通过率60%-80%，100%意味着偷懒
7. 思想层和情感层用通用词，不用原创词

九、反刍机制详细说明（v2.0新增核心功能）
======================================================================

【什么是反刍】
反刍=每次任务完成后，回头检查、蒸馏、更新，让系统越用越聪明。
就像牛吃完草后反刍消化一样，每次任务完成后必须"反刍"这次任务的思考过程，把有用的信息消化吸收进系统。

【反刍的4个检查项】

检查1：思考过程是否蒸馏
- 本次任务的思考过程中，有没有"以后还会用到的关键信息"？
- 角色卡相关的→蒸馏进角色卡蒸馏版.txt
- 非角色卡相关的→蒸馏进非角色卡蒸馏版.txt
- 项目核心信息→蒸馏进项目记忆_蒸馏版.txt
- 蒸馏原则：只记关键信息，不记完整过程，每条1-3句话

检查2：命令是否通过管理员卡执行
- 本次任务是否按标准流程执行了？（第一步到第十一步）
- 是否跳过了某些步骤？（特别是反刍检查）
- 如果跳过了，为什么？下次怎么避免？

检查3：角色卡是否需要调整
- 本次任务中，业务角色卡有没有表现出不足？
- 有没有需要微调的地方？（如分析卡的分析维度、向量卡的检索策略、匹配卡的匹配规则）
- 小调整→自主执行，记录在运行记录
- 重大调整→记录在运行记录，等用户同意后执行

检查4：世界书是否需要调整
- 本次任务中，通用世界书的规则有没有不够用的地方？
- 有没有需要补充的规则？（如新的反偷懒规则、新的质量检查项）
- 小补充→自主执行，记录在运行记录
- 重大修改→记录在运行记录，等用户同意后执行

【反刍的输出】
反刍检查的结果必须写进运行记录的"反刍检查"栏，不能跳过。
反刍后如果有更新（蒸馏版、项目记忆、角色卡、世界书），必须实际执行更新，不能只说不做。

【反刍的价值】
- 每次任务都让系统更聪明一点
- 角色卡越用越准，世界书越用越完善
- 不会重复犯同样的错误
- 关键信息不会丢失（蒸馏后永久保存）

5. 每次任务反刍（第九步）增加一项"界面整洁检查"：
   - 确认主目录只有4个核心文件
   - 确认无散落临时脚本/探查产物
   - 确认新产生的备份已归入「一念永恒小说/子文件夹/版本备份/」

     · lists/：跑批清单和模板（各书清单.txt、模板_*.txt）
     · logs/：运行日志（*.log、*.pid）
     · batch_history/：历史跑批/验证文件夹归档（batch_*/verify_*）
   - 通用Python脚本放入「一念永恒小说/脚本工具/所有的py/」
   - 连载版本专用脚本放入「连载版本/」
   - 禁止把脚本散落在中转API根目录、主目录、或各业务文件夹
   - 临时探查脚本（dump_*/probe_*/tmp_*）用完即删，不进索引
   - 一次性生成脚本（generate_*/update_*/build_*）放入对应分类，用完可归档

- 【研究结论】WebAI2API-main开源项目（Node.js）核心思路=用 page.waitForResponse 拦截网站内部 chat/completion 的 SSE/流式响应，而非DOM轮询。它的 Camoufox 反检测+拟人输入+多窗口并发/负载均衡值得借鉴，但我们环境已用 Playwright+独立profile+独立端口，架构无需重写。
- 【根因定性】qwen_bridge 早就是 v2.0 SSE拦截版（所以稳定），kimi/glm 还是老的 DOM轮询版（轮询DOM等待3次稳定=慢+易超时）。这是 kimi复读/glm超时的根本原因。
- 【glm修复成功】探测发现 chatglm.cn 内部API端点 POST /chatglm/backend-api/assistant/stream（标准SSE，data: JSON）。glm_bridge.py 升级 v2.0：page.expect_response 拦截该端点 → 解析 data: 流（parts[].content[].type=think跳过 / text累加 / status=finish结束）→ 需按 logic_id+text 去重（智谱每帧返回完整文本非增量）。实测 10.5秒返回，不再超时。
- 【kimi修复成功】探测发现 kimi.com 内部端点 POST /apiv2/kimi.gateway.chat.v1.ChatService/Chat，协议=Connect-Web（application/connect+json），4字节大端长度前缀帧+JSON，帧间夹杂gRPC头字节需容错跳过。kimi_bridge.py 升级 v2.0：拦截该端点 → 解析帧（op:set+mask:block.text起始 / op:append+mask:block.text.content增量累加 / think跳过 / done或MESSAGE_STATUS_COMPLETED结束）。实测 9-15秒返回，不再复读。
